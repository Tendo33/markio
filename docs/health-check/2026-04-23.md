# 2026-04-23 Markio 仓库健康检查

## Overall Health Score

**80 / 100**：核心 API、JWT 鉴权、任务 owner 隔离、URL SSRF 防线和控制台基础闭环已经比较扎实；当前主要扣分来自容器部署契约漂移、Redis/Memory 双后端观测语义不一致、前端真实流程回归不足，以及 alpha 阶段仍需明确的生产安全边界。

## Top Issues Summary

- `P1` Compose 文档和运行时契约漂移：`compose.yaml` 启用了 Redis，但没有设置 `TASK_QUEUE_BACKEND=redis`，实际会继续使用内存任务后端；容器重建后异步任务状态仍可能丢失。证据见 `compose.yaml:15-17`、`markio/settings/config_model.py:168-171`、`markio/services/runtime.py:17-40`、`docs/REDIS_INTEGRATION.md:23-29`。
- `P2` Redis dashboard 的 SLA 指标只从最近最多 1000 条任务取样，Memory 后端则从当前内存记录全集计算；两个后端在历史任务较多时会给出不同观测口径。证据见 `markio/services/redis_task_manager.py:178-195` 与 `markio/services/task_manager.py:295-315`。
- `P2` Docker 镜像没有在构建阶段编译 Vue 控制台，而是复制仓库中的 `markio/webapp` 产物，容易把过期 bundle 当成生产控制台发布。证据见 `Dockerfile:57-71`、`Dockerfile:84-90` 与 `docs/console_frontend.md:17-34`。
- `P2` 控制台仍缺少浏览器级 E2E 回归面；当前测试能验证构建产物和静态挂载，但覆盖不到 token 保存、分页、轮询、提交、取消/重试和管理员队列操作。证据见 `tests/test_console_frontend.py:52-97`、`docs/console_frontend.md:93-123`。

## Risk Summary

- JWT 仍持久化在 `localStorage`。这不是当前已确认漏洞，因为本轮没有发现直接 XSS 注入点，但未来一旦引入富文本/HTML 渲染或第三方脚本，token 暴露影响会很高。证据见 `frontend/src/api/client.ts:8-24` 与 `docs/console_frontend.md:65-70`。
- 限流仍是单进程内存桶，多 worker 或多实例部署下不能形成全局节流。证据见 `markio/middlewares/rate_limit_middleware.py:35-38`、`markio/middlewares/rate_limit_middleware.py:114-133`。
- 默认 `memory` 任务后端适合本地和 alpha，但在容器、横向扩容和重启恢复场景中容易被误认为已有 Redis 级持久化能力。证据见 `markio/settings/config_model.py:168-183`、`docs/REDIS_INTEGRATION.md:72-96`。

## Recommended Next Actions

1. 先修 Compose 任务后端契约：在容器环境显式设置 `TASK_QUEUE_BACKEND=redis`，并补一条文档/测试防止“Redis enabled 但任务仍走 memory”的误配回归。
2. 统一 dashboard SLA 口径：明确是全量、滑窗还是最近 N 条，并让 Memory/Redis 两个后端使用同一个指标语义。
3. 把 Docker 控制台构建纳入镜像构建链路，或明确禁止镜像发布依赖仓库中预构建的 `markio/webapp`。
4. 增加最小前端 E2E smoke：覆盖保存 token、任务列表加载、提交页校验、详情轮询和 admin queue 可见性。

整体判断：Markio 的应用层安全和任务隔离已经比一般 alpha 项目更成熟，尤其是 `/v1/*` JWT、任务 owner scope、URL SSRF 防护和上传输出目录约束。当前最大的业务风险不在单个解析器，而在“部署者以为自己启用了 Redis/生产控制台，但实际运行语义不一致”。这类问题会在试用转准生产时直接影响任务可靠性、排障判断和用户信任。

## 2. 项目全局健康度与架构评估

- 产品目标清晰：Markio 是 API-first 文档解析平台，提供同步 `/v1/parse_*`、异步 `/v1/tasks/*`、SDK/CLI 和 Vue 控制台 `/console`。
- 后端分层基本稳定：`markio/main.py` 负责装配，`markio/routers/` 负责 HTTP 契约，`markio/services/` 管任务/注册/运行时，`markio/parsers/` 落具体解析器，`markio/settings/` 管 env 配置。
- 关键安全边界存在：`markio/main.py:120-125` 对所有 `/v1` router 加 JWT dependency；`markio/routers/task_router.py:147-188` 对列表、stats、dashboard 做 owner scope；`markio/routers/task_router.py:167-209` 对队列管理要求 admin。
- 技术债集中在交付语义：Memory/Redis、Docker/本地、已构建 webapp/源码 frontend 的边界需要更硬的自动化保障。

## 3. 产品逻辑与业务流审查

主业务闭环成立：用户保存 JWT -> 进入控制台 -> 上传文件创建异步任务 -> 列表/详情轮询 -> 失败或取消任务可重试 -> admin 管理全局队列。后端也支持同步文件解析、URL 解析和 SDK/CLI 调用。

主要流失点不在页面本身，而在部署后的运行模型。当前 Compose 启用 Redis 服务和 Redis cache，但因为缺少 `TASK_QUEUE_BACKEND=redis`，任务队列仍落在 `AsyncTaskManager`。这会让用户以为任务状态由 Redis 保护，实际仍依赖本地内存和容器文件系统。

## 4. 已确认问题（按业务影响排序）

### [P1] Compose 启用 Redis 但任务队列仍默认走 Memory

- Location: `compose.yaml:15-17`, `markio/settings/config_model.py:168-171`, `markio/services/runtime.py:17-40`, `docs/REDIS_INTEGRATION.md:23-29`
- Impact: Docker Compose 用户会看到 Redis 服务已启动、缓存可用，却没有得到 Redis-backed task execution；容器重建或横向扩容时，任务状态和队列语义会与文档预期不一致。
- Evidence: 文档明确 Redis 任务后端需要同时设置 `REDIS_ENABLED=true` 和 `TASK_QUEUE_BACKEND=redis`；Compose 只设置了 `REDIS_ENABLED=true`、`REDIS_HOST`、`REDIS_PASSWORD`。运行时只有在 `task_backend == "redis" and settings.redis_enabled` 时才创建 `RedisTaskManager`，否则创建 `AsyncTaskManager`。
- Recommendation: 在 `compose.yaml` 增加 `TASK_QUEUE_BACKEND=redis`，并补 `tests/test_runtime_backend.py` 或文档检查，锁住 Compose 和运行时契约。

### [P2] Redis 与 Memory dashboard SLA 口径不一致

- Location: `markio/services/redis_task_manager.py:178-195`, `markio/services/task_manager.py:295-315`
- Impact: 同一个 dashboard 在不同后端可能展示不同的 `avg_ms/p95_ms/max_ms`，管理员无法稳定判断长期性能趋势。
- Evidence: Redis manager 用 `sample_size = min(max(recent_limit * 20, 100), 1000)` 拉最近样本计算 SLA；Memory manager 从当前 `_records` 中所有 completed/failed 记录计算。
- Recommendation: 明确 SLA 语义并统一实现。若选择滑窗，应在 payload 或文档中标注窗口；若选择全量，应为 Redis 增加专门的 duration index 或聚合存储，避免靠任务列表分页采样。

### [P2] Docker 镜像构建没有编译控制台资产

- Location: `Dockerfile:57-71`, `Dockerfile:84-90`, `docs/console_frontend.md:17-34`
- Impact: 镜像会复制当前仓库中的 `markio/webapp`，但 Dockerfile 没有执行 `cd frontend && npm run build`。如果源码 UI 已变但 webapp 未同步，容器会服务过期控制台。
- Evidence: Docker builder 安装 Python 依赖并下载模型，没有安装 Node 或运行 frontend build；最终镜像直接从 builder 复制 `/workspace`，后端会在 `markio/webapp/index.html` 存在时直接 mount SPA。
- Recommendation: 增加 frontend build stage，将产物复制到 `markio/webapp`；或在发布流程中强制校验 source bundle 与 built bundle 同步。

### [P2] 控制台缺少真实浏览器流程回归

- Location: `tests/test_console_frontend.py:52-97`, `docs/console_frontend.md:93-123`
- Impact: 构建能过不代表控制台可用；token 保存、路由跳转、分页、轮询、文件校验、提交、取消/重试和 admin queue 仍可能在浏览器中回归。
- Evidence: 当前 console 测试验证 `/console/` SPA shell、asset bundle、title 和 fallback page；文档仍声明 “no dedicated frontend E2E suite yet”。
- Recommendation: 增加 Playwright/Vitest browser smoke，先 mock API 覆盖最小关键路径，再逐步接入 ASGI 或本地 API。

## 5. 可能风险

### [P1 Risk] JWT `localStorage` 持久化会放大未来 XSS 影响

- Location: `frontend/src/api/client.ts:8-24`, `docs/console_frontend.md:65-70`
- Impact: 如果后续引入 XSS 面，攻击者可以读取持久化 token 并调用 `/v1/*` API。
- Confidence: 中。当前结果渲染使用 Vue 插值和 `<pre>{{ task.result }}</pre>`，toast message 使用 `innerText`；本轮没有确认直接 XSS 漏洞。
- Recommendation: 保留当前产品边界时，至少增加短生命周期 token、显式过期提示或 session 级选项；长期考虑后端会话或更受控的 token 存储。

### [P2 Risk] 单进程限流不适合多实例防护

- Location: `markio/middlewares/rate_limit_middleware.py:35-38`, `markio/middlewares/rate_limit_middleware.py:114-133`
- Impact: 多 worker/multi-instance 下每个进程各自计数，外部请求可绕过全局保护，解析类重任务更容易被打满。
- Confidence: 高。
- Recommendation: 文档明确当前限流只适合单实例；生产化时切到 Redis/shared store 限流或由网关承担。

## 6. 推断与结构性观察

- URL 安全模块是当前质量高点：`markio/parsers/url_parser.py:106-186` 校验协议、凭据、域名 allowlist、私网地址；`markio/parsers/url_parser.py:252-294` 每跳重定向复验并使用 pinned resolver，SSRF 基线较好。
- 上传输出路径约束也较稳：同步解析通过 `resolve_parser_output_dir()`，异步任务通过 `resolve_strict_output_dir()`，能把保存目录限制在配置的 output base 内。
- Redis task store 已有 owner index、status index、Lua claim/cancel/retry/requeue，说明生产化方向清楚；但正因为实现复杂，越需要让 Compose 和 dashboard 指标契约保持准确。
- 当前 working tree 已包含上一轮修复的变更，审计把这些视为“待用户确认的现有改动”，没有继续修改源码。
