# 2026-04-22 Markio 仓库健康检查

## Overall Health Score

**78 / 100**: 核心解析、鉴权、任务隔离和 URL 安全边界已经形成较完整骨架，但控制台权限体验、SLA 指标正确性与前端交付保障仍有明显短板，继续放大流量前需要先补齐。

## Top Issues Summary

- `P1` 仪表盘 SLA 的 `p95_ms` 计算存在系统性低报，管理端会低估长尾耗时，影响容量判断与性能排障。证据位于 `markio/services/task_manager.py:659-675` 与 `markio/services/redis_task_manager.py:321-337`。
- `P2` 控制台此前向普通用户暴露管理员专属“队列管理”入口，造成错误导航与权限死路。相关入口位于 `frontend/src/layouts/AppLayout.vue:174-184`、`frontend/src/views/Dashboard.vue:28-39`。
- `P2` `/queue` 页面此前只有首屏挂载时会自动拉取状态，管理员在页面内保存/切换 token 后不会自动刷新，形成“已授权但页面看起来没生效”的误导。相关逻辑位于 `frontend/src/views/QueueManagement.vue:182-194`。
- `P2` 前端交付链路仍缺少独立 E2E 保障，当前主要依赖构建和后端路由测试，无法覆盖 token 输入、分页、轮询、取消/重试等真实浏览器回归。文档已明确该缺口，见 `docs/console_frontend.md:65-70`、`docs/console_frontend.md:88-94`。

## Risk Summary

- 当前前端将 JWT 持久化到 `localStorage`，这不是已确认漏洞，但意味着一旦控制台未来引入 XSS 面，就会把长期 API token 暴露为高影响风险。证据见 `frontend/src/api/client.ts:8-24` 与 `docs/console_frontend.md:67-70`。
- 限流实现完全依赖单进程内存桶，在多进程或多实例部署下无法形成全局节流，属于扩容阶段的高概率运维风险。证据见 `markio/middlewares/rate_limit_middleware.py:17-120`。
- 默认任务后端仍可落回内存模式，适合 alpha 和本地开发，但在进程重启、横向扩容与跨实例观测上天然受限；这更像当前阶段的产品边界，而不是代码缺陷。证据见 `markio/services/runtime.py` 与 `markio/settings/config_model.py`。

## Recommended Next Actions

1. 先把控制台权限流补成完整回归面：为管理员入口可见性、token 切换和 `/queue` 拉取补前端测试或浏览器级 smoke。
2. 为 dashboard 指标补一个独立的 SLA/percentile 单测层，避免 memory/redis 两套实现继续漂移。
3. 在不改变当前产品约束的前提下，评估把前端 token 存储缩短为 session 级或引入更明确的“高风险提示 + 过期提示”。
4. 如果准备进入多人或多实例部署，优先把限流与任务队列的生产建议写进运维文档，避免默认配置被误用成准生产方案。

## 3. 已确认问题（按业务影响排序）

### [P1] Dashboard 的 P95 指标会系统性低报

- Location: `markio/services/task_manager.py:659-675`, `markio/services/redis_task_manager.py:321-337`
- Impact: 管理端看到的 `p95_ms` 会偏低，导致对长尾任务延迟的判断过于乐观，影响容量预估与性能告警。
- Evidence: 两套实现都用 `int(len * 0.95) - 1` 取索引；在长度为 2 的样本中，95 分位会落到第 1 个元素而不是最大值。
- Recommendation: 统一改为上取整 percentile 索引，并用单测锁住 memory/redis 两条实现。
- Status: **已在本轮修复**。

### [P2] 普通用户会被引导到管理员专属队列入口

- Location: `frontend/src/layouts/AppLayout.vue:174-184`, `frontend/src/views/Dashboard.vue:28-39`
- Impact: 普通用户在主导航和快捷操作都能看到“队列管理”，点击后只能落到无权限提示，造成误导和无效操作。
- Evidence: 入口展示此前不依赖 `isAdmin`，而实际队列接口由后端 `role=admin` 限制。
- Recommendation: 在前端入口层直接按角色裁剪管理员能力，只保留用户可完成的路径。
- Status: **已在本轮修复**。

### [P2] 管理员在 `/queue` 页切换 token 后不会自动刷新队列状态

- Location: `frontend/src/views/QueueManagement.vue:182-194`
- Impact: 管理员在页面内保存新的 admin token 后，视图不会自动拉取队列健康度，容易误判为 token 无效或后端未更新。
- Evidence: 页面此前只在 `onMounted` 时自动 `refresh()`，`watch([tokenConfigured, currentRole])` 只同步角色，不触发数据刷新。
- Recommendation: 在权限状态变化后重新执行队列健康拉取，并保留非管理员清空状态的逻辑。
- Status: **已在本轮修复**。

### [P2] 控制台缺少独立前端 E2E 回归面

- Location: `docs/console_frontend.md:88-94`, `tests/test_console_frontend.py`
- Impact: 当前可以验证 SPA 是否可构建、是否能被 FastAPI 提供，但无法系统覆盖 token 录入、分页、轮询、取消/重试和管理员流程。
- Evidence: 文档明确写明 “no dedicated frontend E2E suite yet”；现有 `tests/test_console_frontend.py` 主要覆盖静态资源与挂载契约。
- Recommendation: 增加一条最小浏览器 smoke，至少覆盖登录 token、任务列表加载和管理员队列页。

## 4. 可能风险

### [P1] JWT 持久化到 `localStorage` 会放大未来 XSS 的影响半径

- Location: `frontend/src/api/client.ts:8-24`, `docs/console_frontend.md:67-70`
- Impact: 一旦后续控制台引入 XSS，攻击者能直接读取长期 token 并调用后端 API。
- Confidence: 中高。当前没有看到明确 XSS 注入点，所以这是风险而非已确认漏洞。
- Recommendation: 保持当前产品约束不变的前提下，至少补充更显式的安全提示、token 生命周期约束，或评估是否改为 session 级存储。

### [P2] 限流只在单进程内生效，多实例部署会失真

- Location: `markio/middlewares/rate_limit_middleware.py:17-120`
- Impact: 横向扩容后，同一来源请求会绕过全局节流，既削弱保护，也让容量观测不稳定。
- Confidence: 高。
- Recommendation: 在准备生产化时切到共享存储限流，或至少在部署文档中明确“当前限流仅适用于单实例/轻量环境”。

## 5. 推断与结构性观察

- `markio/parsers/url_parser.py` 的 SSRF 防护相对扎实：校验协议、拒绝内嵌凭据、解析并阻断私网地址、每跳重定向复验、响应体限长、直连模式 IP pinning。这个模块已经达到“可以作为安全基线”的水位。
- 任务系统的 memory/redis 双实现总体契约一致，且 `tests/test_task_auth_and_idor.py` 对 owner scope 和 admin queue 做了关键兜底；后续主要风险在“指标一致性”和“部署语义”而不是权限越权。
- 控制台的页面边界已经比较清楚，Pinia store 也把 dashboard/list/detail/submit 的请求状态分开维护，这为继续补 UI 回归测试创造了较好基础。

## 6. 测试、可观测性与交付风险

- 后端单测覆盖面不错，特别是 auth、IDOR、URL parser、task manager 这些高风险区域。
- 前端目前主要靠 `npm run build` 和后端静态挂载测试兜底，缺少真实浏览器行为验证，这是最明显的交付短板。
- Dashboard 的 SLA 指标既承担运营观察职责，就不能只靠页面肉眼确认；它已经证明需要专门的数值回归测试。
